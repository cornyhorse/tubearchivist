# UX API contract (backend ↔ frontend)

Status: **draft for agreement with the frontend session**, 2026-10-10.
Built so far: section 1 (queue), section 2 (found videos) and section 3
(add dialog) and section 6 (media server), see
[`fork/jobs-engine.md`](fork/jobs-engine.md).
Spec: MattsTools `docs/architecture/tubearchivist-fork-ux-proposal.md`.

The machine-readable contract is [`ux-api-schema.yaml`](ux-api-schema.yaml)
(OpenAPI 3, generated by drf-spectacular from the serializers in the
backend). A test fails if the schema file and the code drift apart, so the
schema in `main` is always what the backend serves. Browse it live at
`/api/docs/`.

Every endpoint below exists now. Until the PR that builds it is merged, it
answers **501** with `{"error": "not built yet: <step>"}`, where `<step>` is
one of `jobs engine`, `scoped scan and add`, `media server integration`,
`rules API extensions`. The frontend can wire against the routes today and
show a "coming soon" state on 501.

## Conventions

- Auth: session or `Authorization: Token <key>`, like the rest of `/api/`.
  Everything is **admin only** except `GET /api/queue/summary/`,
  `GET /api/rules/presets/` and `GET /api/numbering/schemes/`, which any
  signed in user may read (403 otherwise).
- Errors: `{"error": "plain words"}` with 400 (bad input; DRF field errors
  keep DRF's `{"field": ["msg"]}` shape), 404, 409 (not allowed in the
  current state), 501 (not built yet), 502 (media server failed).
- Times are ISO 8601 with offset. Durations are seconds.
- Lists that page use the existing `paginate` object and `?page=`; new lists
  also accept `?page_size=` (1–500, default the user's page size).
- Bulk actions always take **explicit ids**. "Select all matching" sends the
  same filter object the list was loaded with, never an implicit "all".
- Labels for display (`type_label`, `summary`, `label`, `reason`) are plain
  English made by the backend; keys next to them (`type`, `reason_key`, …)
  are stable for logic, icons and filter chips.

## 1. Work queue — `/api/queue/`

Every unit of work is a **job**. Jobs run in four **lanes** at the same time,
each with its own concurrency and rate limit:

| lane | runs | default concurrency |
|---|---|---|
| `scan` | `check_subscriptions`, `check_channel`, `check_playlist`, `fetch_video` | 2 |
| `download` | `download_video` | 1 |
| `postprocess` | `post_download`, `emby_write`, `media_notify`, `media_refresh` | 1 |
| `maintenance` | `reindex`, `backup`, `restore`, `filesystem_rescan`, `thumbnail_check`, `resync_metadata`, `manual_import`, `index_playlists`, `subscribe`, `version_check`, `snapshot` | 1 |

A subscription check is one `check_subscriptions` job that queues one
`check_channel`/`check_playlist` job per item (its `children`). Each video a
check finds that the rules allow gets a `download_video` job right away, so
downloads start while the check continues.

**Status** `queued → running → done | failed | cancelled`, plus `paused`.
`failed` jobs retry automatically until `attempts == max_attempts`.

**Priority** is an integer, higher first: user actions 100 (`high`),
rule-driven and default 50 (`normal`), schedules 10 (`low`). Within a
priority, older first. `position` is the 1-based place in its lane while
queued.

**Nothing is dropped.** Asking for a job whose type and target already has a
queued or paused job returns that job (`merged: true`, HTTP 200 instead of
201), raises its priority to the higher of the two and increments `merged`.
A running job with the same target is not merged: the new one queues behind
it.

**Actions** (`actions` on each job lists what is allowed right now):

| action | from | effect |
|---|---|---|
| `stop` | running | asks the job to stop; it ends `cancelled` |
| `cancel` | queued, paused | ends `cancelled` without running |
| `pause` | queued (running: stops it, then paused) | not picked until resumed |
| `resume` | paused | back to queued, same priority |
| `retry` | failed, cancelled | a fresh queued run, `attempts` reset |
| `move_to_top` | queued, paused | priority = highest queued in its lane + 1 |

Endpoints:

| method | path | body / query | response |
|---|---|---|---|
| GET | `/api/queue/summary/` | | `QueueSummary` `{running, queued, paused, failed_24h, lanes[]}` |
| GET | `/api/queue/jobs/` | `lane, status, type, target, created_by, parent, page, page_size` | `{data: Job[], paginate}` |
| POST | `/api/queue/jobs/` | `{type, target_id?, priority?}` | 201/200 `{job, merged}` |
| GET | `/api/queue/jobs/<id>/` | | `Job` |
| POST | `/api/queue/jobs/<id>/action/` | `{action}` | `Job`, 409 if not allowed |
| POST | `/api/queue/jobs/action/` | `{action, ids[]}` | `{changed[], skipped{id: reason}}` |
| GET | `/api/queue/lanes/` | | `Lane[]` |
| PATCH | `/api/queue/lanes/<lane>/` | `{paused?, concurrency?, min_interval_seconds?}` | `Lane` |
| GET | `/api/queue/scheduled/` | | `ScheduledJob[]` with `next_run` |
| PATCH | `/api/queue/scheduled/<name>/` | `{enabled}` | `ScheduledJob` |
| POST | `/api/queue/scheduled/<name>/run/` | | 201/200 `{job, merged}`; for `download_pending` the last download job queued, `job: null` if nothing was waiting |

`status` accepts a comma list, or `active` (queued,running,paused; sorted
in run order: running first, then by priority and age) or `history`
(done,failed,cancelled; newest finished first). The Queue page sections map
to: Running now = `status=running`, Up next = `status=queued,paused`,
History = `status=history`, Scheduled = `/scheduled/`.

`Job.progress` (running jobs only): `{fraction, message, speed, eta_seconds,
current, total}`. Poll `GET /api/queue/jobs/?status=running` every 1–2 s
while the page is open; poll `/summary/` every 5–10 s elsewhere.

`Job.result` is set when a job ends, e.g. `check_channel`:
`{"found": 12, "allowed": 9, "ignored": 3, "queued_downloads": 9}`;
`media_notify`: `{"status_code": 204, "paths": 14}`.

"Check channels for new videos" = `POST /api/queue/jobs/`
`{"type": "check_subscriptions"}`. "Check now" on a channel row =
`{"type": "check_channel", "target_id": "<channel_id>"}`.

The old `/api/task/` endpoints keep working during the transition.

## 2. Found videos — `/api/found/`

Videos TA knows about but hasn't downloaded, each with a rule verdict.

`GET /api/found/` query (all optional): `tab` (`waiting` default,
`ignored`, `failed`, `downloaded`), `q`, `channel` (comma ids), `vid_type`
(comma), `min_duration`, `max_duration`, `published_from`, `published_to`
(dates), `error`, `skipped_by_rule`, `reason_key`, `found_by`,
`downloaded_days` (window of the downloaded tab, default 7), `sort`
(`-found` default; `published`, `duration`, `title`, `channel`, `-` for
descending), `page`, `page_size`.

Response `{data: FoundVideo[], paginate, counts: {waiting, ignored, failed,
downloaded}}`; `counts` apply the current filters except `tab`.

`FoundVideo`: `youtube_id, title, channel_id, channel_name,
channel_indexed, vid_type, duration, duration_seconds, published,
thumb_url, found_at, found_by {kind, label, job_id, playlist_id}, verdict,
state, job {id, status, position, progress} | null, error, downloaded_at`.

`state`: `waiting` (allowed, no job yet), `queued`, `downloading`,
`ignored`, `failed`, `downloaded`. Tabs: waiting = waiting+queued+downloading,
ignored, failed, downloaded.

`verdict` (also used by the add preview and rule preview):
`{allowed, action: download|ignore|skip, reason_key, reason, rule
{scope, target_id, summary} | null, override: download|ignore|null}`.
The badge shows `rule.summary` (e.g. "No Shorts · >10 min") and the row
shows `reason` ("longer than 1 h"); clicking opens the editor for
`rule.scope`/`rule.target_id`.

`POST /api/found/actions/` `{action, ids[]}` or `{action, filter{...}}`
(exactly one). Actions: `download_now` (high priority jobs), `download`
(normal priority), `ignore`, `forget` (remove from found), `download_anyway`
(per-video override + job), `always_ignore` (per-video override),
`clear_error`. Response `{matched, changed, job_ids[]}`.
"Download all allowed" = `{"action": "download", "filter": {"tab": "waiting"}}`.

## 3. Add dialog — `/api/add/`

`POST /api/add/preview/` `{urls, rule?, newest_n?}` — `urls` is the pasted
text (one or many links or ids). Stores nothing. Reads YouTube (flat
listing), so allow a few seconds per channel; results are cached 10 min per
link so changing the draft `rule` re-runs instantly.

Response `{items: PreviewItem[], errors: [{url, error}]}`, each item:
`url, kind (video|channel|playlist), id, title, channel_id, channel_name,
thumb_url, video_count, subscribed, known {downloaded, waiting, ignored},
rule (effective rule ref or null), numbering {scheme, source}, verdict
{total, download, skipped, already_have, reasons: [{key, label, count}]},
sample: up to 50 newest with {youtube_id, title, vid_type,
duration_seconds, published, known, verdict}`.

"142 videos: 118 will download, 24 skipped (Shorts 20, >1 h 4)" =
`verdict.total`, `download`, `skipped`, `reasons`.

`POST /api/add/` `{urls, mode, newest_n?, rule?, save_rule?, numbering?,
download_now (default true), priority (default high)}`:

- `mode=subscribe`: subscribe, then check now. `save_rule` defaults true
  (the rule is stored on the channel/playlist).
- `mode=once`: check now and download what the rule allows, no subscription.
  `save_rule` defaults false (the rule applies to this add only).
- `mode=newest_n`: like `once`, limited to the `newest_n` newest videos.
- `numbering` sets the channel's/playlist's scheme.
- For playlists a rule is always one-off for now (stored playlist rules
  arrive with the rules API step); stored channel and default rules don't
  apply to playlist checks yet, as before.

Response 201 `{jobs: Job[], errors[]}` (400 with the same shape when no
link could be read) — one high priority scan job per link (`check_channel`, `check_playlist` or `fetch_video`); follow them in
the queue.

## 4. Rules — `/api/rules/`

Precedence, first match wins: **per-video override** → **playlist rule**
(for videos found by checking that playlist) → **channel rule** →
**default rule** → no rule (download everything). A disabled channel or
playlist rule means "no rule here", not "fall back to the default".

The rule body is today's `DownloadRule`: `enabled, min_duration,
max_duration, vid_types[], title_include, title_exclude (regex),
published_after, action (ignore|skip)`; responses add read-only `summary`.

| method | path | body / query | response |
|---|---|---|---|
| GET | `/api/rules/` | | `{data: [{scope, target_id, target_title, target_subscribed, rule}]}` |
| GET | `/api/rules/presets/` | | `[{key, label, description, patch, needs_value, value_field}]` |
| GET/PUT/DELETE | `/api/rules/default/` | rule body | rule or `null` / 204 |
| GET/PUT/DELETE | `/api/rules/<channel\|playlist>/<id>/` | rule body | rule or `null` / 204 |
| POST | `/api/rules/preview/` | `{scope, target_id?, rule?, limit=50}` | `{total, download, skipped, reasons[], videos[]}` |
| GET | `/api/rules/effective/` | one of `video, channel, playlist` | `{source, rule, override}` |
| GET | `/api/rules/videos/` | | `{data: VideoOverride[]}` |
| PUT/DELETE | `/api/rules/videos/<youtube_id>/` | `{override: download\|ignore, note?}` | `VideoOverride` / 204 |

Presets are chips that merge `patch` into the rule being edited: `no_shorts`,
`no_livestreams`, `skip_over_1h`, `only_over_1h`, `only_after_date`
(`needs_value: date`, `value_field: published_after`), `title_contains`,
`title_excludes` (`needs_value: text`).

The preview runs against the last `limit` videos TA knows for the target
(found and downloaded), newest first; for the default rule, across all
channels.

The existing `GET/POST /api/download/rule/` and the `download_rule` field on
`/api/channel/<id>/` keep working.

## 5. Numbering — `/api/numbering/`

| method | path | body / query | response |
|---|---|---|---|
| GET | `/api/numbering/schemes/` | | `[{key, label, description, frozen, playlist_only, example}]` |
| GET | `/api/numbering/<channel\|playlist>/<id>/` | | `{kind, id, title, scheme, episodes, manual, sample[20]}` |
| POST | `/api/numbering/<kind>/<id>/preview/` | `{scheme}` | `{scheme, episodes, renumbers, sample[]}` with old and new names |
| PUT | `/api/numbering/<kind>/<id>/` | `{scheme}` | `{scheme, renumbered, job_id}` |
| GET | `/api/numbering/video/<youtube_id>/` | | `{data: [{series_kind, series_id, series_title, scheme, season, episode, name, manual}]}` |
| PUT | `/api/numbering/video/<youtube_id>/` | `{series_kind, series_id, season, episode}` | that row; 409 if the slot is taken |
| DELETE | `/api/numbering/video/<youtube_id>/` | `?series_kind=&series_id=` | 204 |

Names look like `S2025E6200 - Southern California Trains 2025`. Show the
preview's "this renumbers N episodes in Emby" before calling PUT. Manual
numbers survive scheme changes. PUT queues an `emby_write` job.

The existing `emby_numbering` field on channel and playlist keeps working.

## 6. Media server — `/api/mediaserver/`

| method | path | body | response |
|---|---|---|---|
| GET | `/api/mediaserver/` | | settings |
| PUT | `/api/mediaserver/` | settings | settings |
| POST | `/api/mediaserver/test/` | `{type?, url?, api_key?}` (unsaved form values) | `{ok, server_name, product, version, error}`, always 200 |
| GET | `/api/mediaserver/libraries/` | | `{data: [{id, name, collection_type, paths[], contains_ta}]}`; 409 not configured, 502 server error |
| POST | `/api/mediaserver/notify/` | `{paths[]}` or `{all: true}` | 201 `{job}` |
| POST | `/api/mediaserver/refresh/` | `{library_id?}` | 201 `{job}` (full refresh, for repairs) |

Settings: `type (emby|jellyfin|null = off), url, api_key (write-only),
api_key_set, api_key_source (env|db|null), library_id, path_from
(read-only, TA_EMBY_ROOT), path_to (same folder as the server sees it),
notify_enabled, debounce_seconds, last_notify {at, status_code, paths,
job_id, error}`.

The API key is never returned. On PUT: omit `api_key` to keep it, send
`""`/`null` to clear it. If `TA_MEDIASERVER_API_KEY` is set, it wins and
`api_key_source` is `env` (show the field as "set by the environment").

After the Emby writer changes files, TA collects the folders holding the
changes (season and series folders, deduplicated), waits
`debounce_seconds` so more changes join, and sends one
`POST /Library/Media/Updated` (`UpdateType: Modified`, chunks of 500) with
those folders mapped from `path_from` to `path_to`. The server rescans just
those folders. A failed call keeps the folders for the retry. Each call is a `media_notify`
job, so it shows in Queue → History with its status code.

## 7. MCP — `/api/mcp`

Streamable HTTP MCP server, same token auth. Not used by the frontend. Tools
call the same service functions as the endpoints above.
